# 决策支持力（Decision Support）审查

可研报告的**终极用途**是支撑投资决策 —— 投委会成员通常只读摘要 + 结论部分，可能不超过 10 分钟。如果"摘要 + 结论"无法独立成立，就算正文写得再细也不及格。本 skill 站在"读者只有 10 分钟"的角度审查。

## 何时使用

- 用户说："摘要质量"、"决策可读"、"投委会能用吗"、"老板会读得下去吗"
- 在 `report-drafting-chapter-1-overview` 完成后做最后审查
- 在 `report-drafting-chapter-9-conclusion` 完成后做配对审查
- 在终稿前最后一遍把关

## 工作流

```
1. report_get_section 第 1 章总论 + 第 9 章结论与建议
2. 模拟"投委会读者"通读 → 用 5 个核心问题质询
3. 每答不上来 / 答不清楚 → 写 high/medium issue
4. review_start 写入 issue_center
```

## 投委会读者的 5 个核心问题

任何一份可研，决策者读完摘要 + 结论后应该能脑子里立即答得出：

### 问题 1：这是什么项目？

要素：
- 项目名称（含主要业务定位）
- 建设单位（含资质 / 信用 / 历史项目）
- 选址（精确到行政区 + 园区 / 地块）
- 行业 / 子行业分类
- 投资性质（新建 / 改扩建 / 并购）

如果一句话讲不清，是**high issue**。

### 问题 2：为什么必要 / 必要性论证站得住吗？

要素：
- 政策驱动力（一两条关键政策）
- 市场驱动力（缺口 / 增长趋势）
- 技术驱动力（如有）
- 区域 / 战略层驱动力

如果"必要性"段落变成抽象口号（"响应国家战略"），缺一两条**可量化的依据**，是 **medium issue**。

### 问题 3：投多少、谁出钱？

要素：
- 总投资（动态 / 静态需明示）
- 资本金 vs 融资比例
- 主要资金来源（自有 / 银行 / 基金 / 补贴）
- 现金流缺口高峰期及对应安排

任何一项数字与正文不一致 → **high issue**（关联 `doc-review-numerics-cross-check`）。

### 问题 4：经济上划得来吗？

要素：
- 财务 IRR（全投资 / 资本金，税前 / 税后 4 选明示）
- NPV @ 行业基准贴现率
- 投资回收期
- 与行业 benchmark 对比（baseline）
- **核心敏感性结论**（哪个变量最敏感、临界点）

如果只给一个 IRR 数字不说前提（如"IRR 12%"但没说全投资还是资本金，税前还是税后），是 **medium issue**。

### 问题 5：风险大吗 / 怎么管？

要素：
- 3-5 个最关键风险（不要 10+ 个琐碎风险）
- 每个风险的应对策略（具体到组织 / 制度 / 财务）
- 残留风险水平的定性判断（可接受 / 需关注 / 不建议）

如果风险章节只是抽象罗列没对策（"加强管理"），是 **medium issue**。

## 摘要写作 8 项审查 checklist

| # | 项 | 通过标准 |
|---|---|---|
| 1 | 长度 | 800-1500 字（投委会读 5 分钟） |
| 2 | 数字密度 | 关键 5-8 个数字（多了反而记不住） |
| 3 | 结论前置 | 第 1 段直接出投资 / IRR / 结论判断 |
| 4 | 不抽象 | 没有"积极推进 / 重要意义" 类空话 |
| 5 | 不堆术语 | 没有未解释的专业缩写 |
| 6 | 风险显眼 | 高风险点用粗体 / 单独段 |
| 7 | 建议明确 | 结论说"建议批准" / "建议条件批准（需补 XX）" / "不建议" |
| 8 | 可量化 | 每个论点至少一个数字或政策依据 |

## 第 9 章"结论与建议" 写作审查

结论章应该是**摘要的扩展版**，但有额外要求：

| 段落 | 必含要素 |
|---|---|
| 9.1 结论 | 项目可行性的定性判断 + 量化依据 |
| 9.2 建议 | 立项决策 / 后续工作 / 实施保障 三类建议 |
| 9.3 待解决问题 | 评审应回应的疑点 / 风险 / 待补充信息 |

第 9 章常见问题：
- **结论自相矛盾** —— 正文风险评估说"高风险"，结论说"高度可行"
- **建议过于宽泛** —— "建议批准"但不说附加条件
- **回避问题** —— 风险章节列出来的风险在结论里没提及

## 审查 SOP

### 步骤 1：扮演角色读

把自己想象成投委会成员，只读 1 章摘要 + 9 章结论。**关掉对正文细节的记忆**。

### 步骤 2：用 5 问质询

逐条问"是不是答得出 / 答得清楚 / 信不信"。

### 步骤 3：交叉印证

抽样核对：
- 摘要里的 IRR ↔ 正文 6 章 IRR
- 摘要里的总投资 ↔ 5 章估算总表
- 摘要里的风险 ↔ 7 章风险分析

任何一处不一致 → 立即写 issue。

### 步骤 4：写 issues

```json
{
  "anchor": "1.3 主要结论",
  "comment": "结论段缺失关键 IRR 前提：写「IRR 11.5%」未注明是全投资还是资本金，税前还是税后。建议改为「项目资本金 IRR（税后）11.5%，超过行业基准贴现率（10%）1.5 个百分点」。",
  "severity": "medium",
  "category": "决策可读性"
}
```

## 严重度判定

| 等级 | 标准 |
|---|---|
| **high** | 5 大问题中至少 1 个**完全答不出**；或摘要与正文严重不一致 |
| **medium** | 5 大问题答得出但**关键前提模糊**（如 IRR 没说全 / 资本金，税前 / 税后） |
| **low** | 行文 / 结构小问题（如建议过于抽象、缺粗体强调） |
| **info** | 格式建议 |

## 边界

- **不替决策者下判断**：不写"我认为应该批准/不批准"，而是评估"决策依据是否充分"
- **不重写正文**：发现摘要薄弱 → 写 issue 让用户主导改稿，agent 可用 `report_propose_section` 提建议版

## 配套工具

- `report_get_section section_id=<第1章对应的 section_id>` / `report_get_section section_id=<第9章对应的 section_id>`：分章读关键章节
- `report_list_sections`：拿章节摘要快速判断
- `review_start` + issues：写入
- `report_propose_section`：如发现关键缺失要提议补内容

## 与其他 skill 的协同

- 配合 `doc-review-numerics-cross-check`：核对摘要数字与正文一致
- 配合 `doc-review-risk-completeness`：确认风险有写进摘要
- 配合 `report-drafting-chapter-1-overview` / `chapter-9-conclusion`：写作与审查互补
